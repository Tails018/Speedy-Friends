# Eliminación experimental de fanarts — solo servidor

Este módulo **no está conectado a la página ni despliega un endpoint**. El sistema actual sigue funcionando igual, incluidos los tokens heredados; todavía no se ha mitigado su exposición. Tampoco incorpora credenciales ni SDK de Cloudinary. No utilizarlo en producción hasta implementar y comprobar las condiciones siguientes.

El llamador debe ser una función callable de Firebase que recibe `request.auth.uid` del runtime tras verificar el token; jamás construya `request.auth` con datos del usuario. El cliente envía solo `{assetId}`: no se aceptan propietario, UID, rol, public ID ni tipo del recurso enviados por el navegador. Los adaptadores son código privilegiado del servidor.

## Contrato indispensable de los adaptadores

1. `claimDeletion({assetId, actorUid})` debe obtener un vínculo de recursos de un catálogo **privado, escrito exclusivamente por el servidor**, autorizado mediante reglas y/o Admin SDK. El fanart actual y sus campos `cloudinaryPublicId`, `ownerUid` y `cloudinaryDeleteToken` no son por sí solos una fuente suficiente: algunos son editables o creados por el cliente. El vínculo debe generarse a partir de subidas verificadas por servidor o migrarse tras una revisión confiable, sin copiar ni publicar tokens.
2. La misma transacción debe validar que el actor sea propietario o administrador mediante una fuente de autoridad que los usuarios no puedan escribir y devolver `authorization` igual a owner o `admin`; el módulo vuelve a comprobar que el UID coincida con el propietario para owner; validar también activos, revocaciones y el identificador; reservar una generación inmutable para un solo proceso, con `lockId` aleatorio, recuperación de bloqueos y expiración compatibles con reintentos. La verificación debe aplicarse también antes de devolver `already-deleted`; nunca debe indicar al no autorizado si un recurso existe.
3. `destroyCloudinary(publicId, options)` debe usar el SDK oficial configurado solo en servidor con credenciales obtenidas de un gestor de secretos, no del navegador ni del repositorio. Se envía `resource_type` desde el vínculo confiable y `invalidate: true`. Cloudinary usa el tipo `video` también para audio. Una excepción o respuesta desconocida se considera fallo y no se finaliza el estado de la base.
4. `completeDeletion({assetId,lockId})` debe comprobar mediante transacción que el bloqueo y la generación siguen siendo los mismos, dejar una lápida inmutable auditable y permitir recuperación idempotente ante una caída. Si Cloudinary devuelve `not found` tras un reintento reservado, puede finalizar. La eliminación en Cloudinary y el estado de Firebase no constituyen una transacción distribuida; se necesitan cola, reconciliación y pruebas de fallos parciales.

Las pruebas unitarias utilizan adaptadores simulados; comprueban entradas, separación de datos, rechazo de solicitudes, manejo de errores y flujo de reintentos. **No validan un endpoint real, reglas, proveedor de identidad, bloqueo, credenciales, permisos Cloudinary ni una migración.** Antes de activar el sistema faltan las implementaciones confiables de esos adaptadores, protección del catálogo, pruebas del emulador para propietario/admin y ataques concurrentes, reglas, frontend y plan de migración y reversión. No se ha llamado a Cloudinary ni se han borrado medios.

Documentación oficial: [Cloudinary, eliminación de recursos](https://cloudinary.com/documentation/delete_assets), [Cloudinary, API destroy](https://cloudinary.com/documentation/image_upload_api_reference), [Firebase callable](https://firebase.google.com/docs/functions/callable). La invalidación de CDN no es instantánea y puede depender de la configuración de la cuenta.
